============================================================
12. DEFINIÇÃO DE COLD E WARM
============================================================

Documentar a definição usada.

COLD LOCAL

- novo processo;
- checkout limpo;
- primeira execução depois de limpeza segura dos artefactos do projeto, quando aplicável;
- caches globais de Flutter, Dart, Pub e SDK preservadas;
- sem eliminar SDKs ou caches globais.

WARM LOCAL

- mesmo commit;
- mesmo ambiente;
- sem `flutter clean`;
- dependências já resolvidas;
- repetição imediata após uma execução válida.

COLD CI

- cache miss real ou chave nova;
- queue separada da execução.

WARM CI

- mesmas versões e lockfiles;
- cache hit confirmado nos logs.

Não classificar uma execução como cold ou warm sem evidência do estado das caches.

20. SHARDING DETERMINÍSTICO
============================================================

Avaliar inicialmente 4 shards.

O número final deve resultar das medições.

Equilibrar por duração histórica, não apenas por quantidade de ficheiros.

Cada ficheiro de teste deve pertencer:

- a exatamente um shard;
- nunca a zero;
- nunca a dois, salvo duplicação intencional documentada.

Criar validação automática do manifest.

A validação deve:

- descobrir todos os `*_test.dart`;
- comparar com o manifest;
- falhar por ausência;
- falhar por duplicação;
- falhar por caminho inexistente;
- apresentar diff claro.

Preferir manifest determinístico versionado quando o sharding nativo não equilibrar adequadamente.

Quando usar sharding nativo:

- provar reprodutibilidade;
- medir equilíbrio;
- justificar.

Registar duração de cada shard.

Minimizar o shard mais lento.

Criar classificador determinístico e conservador.

Categorias:

DOCUMENTAÇÃO

Inclui Markdown e ficheiros sem impacto runtime.

Pode evitar Android.

CÓDIGO DART SEM UI

Exige:

- analyze;
- testes focados;
- suíte completa sharded no CI.

UI OU NAVEGAÇÃO

Exige:

- analyze;
- testes focados;
- suíte sharded;
- Android smoke.

BASE DE DADOS OU INICIALIZAÇÃO

Exige:

- tudo o anterior;
- clean install;
- upgrade relevante.

PIPELINE OU TESTES

Exige:

- validação comparativa;
- suíte completa;
- CI real;
- auditoria de testes.

RELEASE

Exige Release Gate completa.

Ficheiro de produção desconhecido deve receber a categoria de maior segurança aplicável.

Uma alteração de produção nunca pode evitar a suíte completa do CI.

============================================================
25. GITHUB ACTIONS
============================================================

Auditar primeiro:

.github/workflows/flutter_quality_gate.yml

Antes de renomear qualquer workflow, job ou check:

- identificar o nome mostrado no GitHub;
- identificar o required check;
- distinguir workflow, job e check run;
- preservar o nome requerido.

Não alterar branch protection.

Estrutura desejada:

1. classificação;
2. análise e contratos;
3. matriz de shards;
4. Android smoke condicional;
5. agregador final estável.

Implementar quando comprovado útil:

- `concurrency`;
- grupo por PR ou branch;
- `cancel-in-progress: true`;
- cache de Flutter através do mecanismo oficial já usado ou suportado;
- cache Pub;
- cache Gradle;
- chaves baseadas em versões e lockfiles;
- restore keys seguras;
- timeouts explícitos;
- logs claros;
- summaries pequenos;
- artefactos de falha;
- retenção curta;
- permissões mínimas.

Não cachear o SDK Flutter cegamente sem medir ou sem suporte oficial do setup usado.

Evitar:

- várias instalações de Flutter no mesmo job;
- `pub get` repetido sem necessidade;
- analyze duplicado;
- suíte completa sequencial depois dos shards;
- builds APK duplicados;
- uploads grandes em runs verdes;
- caches de diretórios inseguros;
- chaves demasiado amplas;
- acesso desnecessário a secrets.

Qualquer nova action externa deve:

- ser necessária;
- ter reputação adequada;
- estar fixada a versão imutável ou commit SHA;
- ter risco documentado.

============================================================
26. GATE AGREGADOR
============================================================

O agregador deve:

- ter nome estável;
- depender de todos os jobs obrigatórios;
- falhar quando qualquer job obrigatório falha;
- tratar corretamente `success`, `failure`, `cancelled` e `skipped`;
- aceitar apenas skips previstos pela classificação;
- não repetir testes;
- ser adequado a branch protection.

Um shard falhado deve falhar o agregador.

Um Android smoke obrigatório falhado deve falhar o agregador.

Quando o required check não puder ser preservado sem alteração manual da branch protection:

PARAR E REPORTAR.

============================================================
27. CI REAL E TESTE DE FALHA
============================================================

Validar num Pull Request real.

Confirmar:

- jobs arrancam;
- shards correm em paralelo;
- caches restauram;
- cancel-in-progress cancela runs obsoletas;
- alteração de documentação não executa Android;
- alteração de produção não evita a suíte completa;
- agregador reflete dependências;
- logs são diagnósticos;
- permissões são mínimas.

Quando necessário para provar falha de shard:

- usar branch ou commit temporário isolado;
- não contaminar o head final;
- não reescrever história pública de forma destrutiva;
- remover a falha antes do commit final;
- documentar a evidência.

============================================================
29. GPU
============================================================

Avaliar GPU apenas para:

- renderização do emulador;
- animações;
- screenshots;
- responsividade UI.

Não atribuir à GPU ganhos em:

- analyze;
- testes Dart;
- compilação Dart;
- Gradle;
- unit tests do GitHub.

Não instalar:

- CUDA;
- frameworks ML;
- drivers experimentais;
- ferramentas sem relação com o emulador.

Quando houver software rendering e suporte seguro:

1. medir estado atual;
2. ativar host ou auto de forma reversível;
3. repetir as medições;
4. executar smoke várias vezes;
5. manter apenas se houver ganho e estabilidade;
6. restaurar em caso de regressão.

============================================================
30. ANDROID SMOKE
============================================================

Criar ou otimizar um teste Android curto com app real.

Cobertura mínima:

1. app arranca;
2. perfil está disponível ou é criado;
3. Dashboard abre;
4. Treinos abre;
5. treino abre;
6. Adicionar exercício abre;
7. primeiro passo do seletor aparece;
8. 5 contextos aparecem;
9. não existe exceção crítica;
10. Back funciona.

Não repetir:

- full-app completo;
- todos os ecrãs;
- upgrade;
- screenshots extensivos.

Meta com emulador pronto:

até 5 minutos.

Meta desejada:

1 a 3 minutos.

Evitar:

- limpar dados sempre;
- reiniciar AVD sempre;
- recompilar por cenário;
- waits fixos;
- `pumpAndSettle` ilimitado;
- screenshots redundantes.

Capturar logs detalhados apenas em falha ou quando necessários para o relatório.

31. SINCRONIZAÇÃO ANDROID
============================================================

Substituir espera temporal por condição observável.

Todo loop deve ter:

- timeout máximo;
- mensagem de erro útil;
- intervalo razoável;
- exit code real.

Não aumentar timeouts para esconder lentidão.

32. REUTILIZAÇÃO DE BUILD
============================================================

Quando cenários usarem a mesma configuração:

- compilar uma vez;

- instalar uma vez quando seguro;
- executar múltiplos cenários;
- separar dados quando necessário.

Investigar suporte oficial a:

- application binary pré-construída;
- `--use-application-binary`;
- runner existente;
- ADB seguido de testes compatíveis.

Não mudar de runner quando isso reintroduzir problemas conhecidos sem prova.

Documentar limitações do Flutter `integration_test`.

35. METAS DE PERFORMANCE
============================================================

Metas desejadas:

Fast Gate warm:
30 segundos a 2 minutos

PR Gate local warm:
até 5 minutos

Suíte completa no CI sharded:
até 8 minutos de parede

CI de PR warm:
até 10 minutos de execução

CI de PR cold:
até 15 minutos de execução

Android smoke com emulador pronto:
até 5 minutos

Meta mínima global:

30% de redução no caminho crítico comparável

Meta desejada:

40% a 60%

Calcular:

reduction_percent =
((before - after) / before) * 100

Comparar apenas:

- mesmo ambiente;
- mesma cobertura;
- mesma classificação;
- mesma definição cold/warm;
- mesmo tipo de execução.

Separar:

- queue;
- setup;
- execução;
- upload;
- teardown.

Quando uma meta não for atingida:

- entregar ganhos reais;
- identificar gargalo;
- distinguir código, hardware, runner, GitHub queue e limitação externa;
- não falsificar.
